# Open Product Decisions

Routes: [documentation graph](index.md).

Standing records: [ADR 0001: brand owner as client](adr/0001-brand-owner-as-client.md), [ADR 0002: MVP scope deferrals](adr/0002-mvp-scope-deferrals.md), [ADR 0003: dashboard foundation](adr/0003-new-dashboard-foundation.md), [ADR 0004: archive the first dashboard](adr/0004-archive-legacy-dashboard.md).

## Launch roadmap

Plan: [next steps](next-steps/index.md), 30 tasks in execution order. All its decisions, D1 to D13, are resolved. The details and the operational defaults (clean-up after 7 days, a resubmission cap of 3, 60 s polling, 5 registrations per hour per email) are in [its decisions page](next-steps/01-decisions.md). NS-01, NS-02, NS-03 and NS-29 are shipped; Phase 1 continues with NS-30.

- [x] **D1: Filament is retired:** decided 2026-11-09. The Next.js dashboard is the only web surface for every guard, including the whole admin back office. Filament was removed after its replacements shipped (NS-28, done 2026-11-11; the `filament/filament` package and its Filament-only dependencies were removed from `composer.json` and `composer.lock` afterwards, with the user's explicit authorisation).
- [x] **D2: How a new brand owner joins:** decided 2026-11-09. A public "Register your business" page on the dashboard, with email verification, a status page and emails (NS-03). Barbers keep the stylist app's sign-up and get an admin approval queue (NS-30). Clients need no approval; branches and admins are never public.
- [x] **D3: Admin view of branch records:** resolved 2026-11-09. One platform-wide list per screen, with brand and branch filters (NS-09). No pick-a-branch-first mode.
- [x] **D4: Client data for admins:** resolved 2026-11-09. Admins see the account, bans, bookings and reviews written. Face analysis, preference vectors, interaction logs, saved filters, service histories, favourites and discovery preferences are never exposed (NS-07).
- [x] **D5: Dashboard notifications:** resolved 2026-11-09. Polling every 60 s while the tab is visible, and on sign-in. No realtime channel at launch (NS-10).
- [x] **D6: Billing at launch:** resolved 2026-11-09. Manual: the admin assigns plans and payment happens outside the system. NS-26 is deferred until after launch.
- [x] **D7: Barber web scope:** resolved 2026-11-09. Light: schedule, earnings and the account page. Self-service stays in `stylist_app`, and NS-27 closes with no work.
- [x] **D8: Rejection and suspension:** resolved 2026-11-09.
  - Brands gain `rejected` (with a reason; resubmit to `pending`; after 3 resubmissions, "contact support") and `suspended` (with a reason; out of client search; no new bookings; existing future bookings kept unless the admin also cancels them, which notifies the clients; subscription unchanged; the owner and managers sign in to a banner and can't create).
  - Barbers gain `rejected` with the same resubmission cap; the stylist app is synced in the same task.
  - Each transition is row-locked and recorded in `status_change_logs`, with an email and a notification (NS-06, NS-30).
- [x] **D9: Branch approval:** resolved 2026-11-09. The brand approval and the plan's branch limit are the gate. The owner loses the `status` field on branch create and edit, and switching a branch on or off becomes an explicit, checked action. The admin can suspend a branch. No per-branch approval queue (NS-06).
- [x] **D10: Deleted accounts:** resolved 2026-11-09. Deletion anonymises the email, name and phone, keeps the bookings, and frees the email for a fresh account. A banned email stays refused (NS-03).
- [x] **D11: Pending owner early access:** resolved 2026-11-09. Brand profile, plus one branch with its hours, chairs and services. No stylists, invitations, extra branches, client visibility or bookings until approval (NS-03).
- [x] **D12: CAPTCHA:** resolved 2026-11-09. None at launch: limits per IP (5 per minute) and per email (5 per hour), a honeypot field, and verification before the queue. Turnstile only if abuse appears, with package approval (NS-03).
- [x] **D13: Public website:** resolved 2026-11-09. It stays in Laravel, with English and Arabic 404, 500 and 503 pages (NS-29). Content is managed by NS-25.

## Dashboard feature modules

Plan: [feature modules master plan](feature-modules-plan.md) (sections 4 and 12). The plan was checked against the backend routes and Form Requests; these items differed from the original brief. All of them are resolved and every module has shipped; the entries stay as the record of each answer.

Resolved 2026-11-04 (session handover). Remove each entry once its module ships.

- [x] **Barber URL segment:** the dashboard uses the backend name directly: `/dashboard/[guard]/stylists` calls `/stylists`. The UI label stays "Barbers". No path mapping exists in the proxy. The `/barbers/{barber}/services` override routes are a separate Brand-group resource for Module 3.
- [x] **Working hours:** edited through the dedicated `GET|PUT /branches/{id}/opening-hours` endpoint (a partial `PUT /branches/{id}` is rejected, so the editor does not use it). Resolved 2026-11-05: split shifts are supported (up to four non-overlapping shifts per day); the response keeps `opens_time`/`closes_time` as the day's span and adds `shifts`, so mobile builds that predate shifts keep working. Dated overrides stay single-interval.
- [x] **Booking statuses:** audited against the backend; all six `BookingStatus` values are live (`pending`, `confirmed`, `in_progress`, `completed`, `cancelled`, `no_show`). Transitions: pending to confirmed or cancelled; confirmed to in_progress, cancelled or no_show; in_progress to completed, cancelled or no_show; the other three are terminal. `PATCH /bookings/{id}` rejects `pending` as a target, so the UI offers only graph-valid transitions.
- [x] **Barber portal scope:** earnings plus a read-only schedule. The Operations routes reject barbers, so resolved 2026-11-07 with barber-only `GET /dashboard/schedule/appointments` and `GET /dashboard/schedule/hours`. Booking actions and hours editing stay in the stylist app; weekly hours allow one shift per weekday (unique key).
- [x] **Earnings shape and CSV:** `GET /earnings` accepts `from` and `to`. Resolved 2026-11-05: it keeps `{scope, totals[]}` and adds `series[]` (per day and currency: `date, currency_code, gross_minor, completed_bookings_count`), `previous_period` and `previous_totals[]` (the equal range just before; null without a full range), so trends need no second request. No paging. CSV export is generated client-side from loaded rows.
- [x] **Q6 — Earnings charts:** no chart library. Bars are flex rows of Tailwind elements (`components/earnings/bar-chart.tsx`), so RTL, light/dark and `prefers-reduced-motion` follow the page with no dependency. Resolved 2026-11-05.
- [x] **Branches module (owner and admin):** resolved 2026-11-07. The existing `/dashboard/branches` CRUD is used as-is; the only backend change is the optional `status` and `brand_id` list filters. Create and delete are for admins and brand owners (the proxy mirrors `canManageBrand`; branch managers still edit their own branch from Working hours). A brand cannot be changed on an existing branch from the dashboard. Opening hours, tags and the floor plan are not part of the branch form. A brand's plan without `multi_branch` answers 403 `feature_not_enabled` on adding another branch, which the form explains. The admin catalog shipped as Module 12 (see below); admin payouts and plans shipped as Module 9 and Brands as Module 11.
- [x] **Admin Catalog (Module 12):** resolved 2026-11-09. `/dashboard/admin/catalog` gives platform admins full management of the global top-level categories: list with item, subcategory and service counts (status filter and search apply to top-level rows; subcategories are shown read-only), create (slug generated server-side, `universe` optional and defaulting to unisex), edit, activate/deactivate and delete. Delete is allowed only for an empty category (no non-deleted subcategories of any status, no non-deleted catalog items, and no service linked directly or through any of its items, deleted or not); otherwise the backend answers 409 `CONFLICT` and the dashboard offers deactivation instead. Deactivating never cascades to subcategories or items. Catalog items were read-only here at this point; item management moved to the dashboard in NS-21. Deferred, with the reason: inactive subcategories still appear in the public `/service-catalog/categories` tree and items of an inactive category stay visible in `/service-catalog/items`, because changing those public contracts would affect the mobile apps; the dashboard copy says so. `POST /dashboard/service-categories` (operations group, any manager or owner) stays as a deliberate exception to ADR 0002 so the service form keeps its inline create; it now shares the admin name rules and slug generator.
- [x] **Admin payouts and plans (Module 9):** resolved 2026-11-07. The existing `/dashboard/admin/payouts`, `/subscription-plans` and `/subscriptions` endpoints are used as they are; the backend only gains row-locked status changes and the `status` (subscriptions) and `is_active` (plans) list filters. Payouts reuse the `payouts` nav entry (the screen depends on the guard); plans and brand subscriptions are two admin entries. A payout move asks for optional notes, and a transfer reference when marking paid. Plan prices are typed in major units. Commission rules and payment gateways stay "Soon"; settings and analytics shipped as Module 10.
- [x] **Platform analytics and settings (Module 10):** resolved 2026-11-07. Admin analytics use `GET /admin/analytics/overview`, extended additively with a `from`/`to` range, plan names, a booking status mix, a daily completed series and platform totals; money is never summed across currencies. Owner analytics are not a new endpoint: the owner's brand-scoped figures, trend and chart already live on Earnings (`/earnings`, `/overview`), so Analytics is admin only and other guards get the forbidden state. Platform settings use the existing `GET|PATCH /admin/settings` with two new cross-field rules (default page size at most the maximum; sign-in lifetime at least the session lifetime), mirrored in the form. Labels and units are dashboard dictionary text keyed by `setting_key`; a key the dictionary does not know shows its raw key. No chart library (the Earnings bar chart is reused). Commission rules and payment gateways stay "Soon".
- [x] **Admin Brands (Module 11):** resolved 2026-11-08, approve-only. Admins get `/dashboard/admin/brands`: the pending queue by default (`status=all` and `active` in the URL), name search, a detail dialog read from the existing `GET /dashboard/brands/{brand}`, and Approve behind a confirmation through `PATCH /dashboard/admin/brands/{brand}/approve`. No reject or suspend status, no admin create/edit, no feature-flag panel. The backend goes slightly past "a status filter only", because `backend/CLAUDE.md` requires policies and FormRequests: `BrandPolicy` gains `approve` (admin only) and `viewAny` (admin or brand owner), called by the approve action and the dashboard list, and the list moves to `ListDashboardBrandsRequest` (`status` enum, `search`, `page`; `per_page` is still clamped, never a 422, so the brand pickers keep asking for 100). `BrandResource` is unchanged and the mobile apps never call these routes. Approval records no audit trail, and search matches the brand name only, not the owner email (both deferred). Updated 2026-11-09: the branch-create and assign-plan brand pickers ask `GET /dashboard/brands?status=active`, so pending brands are no longer offered; branch list labels and the branch brand filter still show every brand. This is a dashboard filter, not enforcement: `POST /dashboard/branches` and `POST /dashboard/subscriptions` still accept a pending brand (refusing it on the backend stays a deferred follow-up). Product rule: an owner whose brands are all pending cannot create a branch from the dashboard; the dialog says the brand is waiting for approval. Approving a brand refreshes the pickers in the approving admin's session; an owner already signed in sees the approved brand after a reload or once the 5-minute option cache expires.
- [x] **Admin privilege model:** resolved 2026-11-11. Equal privileges for every active admin stay (invite and deactivate admins, platform settings, payouts, plans, bans). The `admins` table keeps no role column and no RBAC is added until the business names roles (for example finance or support). The last-active-admin and self-deactivation guards (NS-04) stay.
- [x] **Legacy activation routes (barber and branch):** resolved 2026-11-11. API compatibility is kept (same paths, `201`, `ActivationLogResource`), but they follow the authoritative rules. `POST /admin/branches/{branch}/activate|deactivate` call `BranchLifecycleService` first (suspended stays suspended with 409, brand approval, plan limit, last-active rule, status history). `POST /admin/barbers/{barber}/activate|deactivate` and `POST /branch/barbers/{barber}/activate|deactivate` refuse a pending or rejected barber with `409` and code `barber_not_approved`, so only the review queue (NS-30) can approve a barber; repeating an on or off for an approved barber stays allowed. The admin routes now record the acting admin in `activation_logs.activated_by_id`. The barber self routes (`POST /barbers/{barber}/activate|deactivate`, live in the stylist app) are unchanged: their middleware already refuses pending and rejected barbers. No client calls the admin routes, and the dashboard proxy does not forward them.
- [x] **D9 amendment, branch switch permission:** resolved 2026-11-11. Only the owner and the platform admin switch a branch on or off (`PATCH /dashboard/branches/{branch}/switch-on|switch-off`); a branch manager gets 403 from the route middleware and the dashboard proxy allow-list no longer forwards the call (guard `BRANDS`). This replaces the earlier NS-06 wording that let managers switch; D9 itself only says switching is an explicit, checked action.
- [x] **Branch applications are read-only on GET:** resolved 2026-11-11. `GET /branch/job-postings/{id}/applications` never writes; the explicit `POST /branch/job-postings/{id}/applications/mark-seen` marks them seen (the Business app calls it before listing). Known limit: Business app builds released before commit `32d66844` still rely on the GET and no longer clear the unseen state; they recover when the app is updated.
- [ ] **Barber self-reactivation after an admin deactivation (open, found 2026-11-11):** the stylist app's `POST /barbers/{barber}/activate` lets any approved barber switch themselves on, including one an admin switched off through NS-08 (`activation_logs.activated_by_id` is set only for admin moves). Decide whether an admin deactivation should block self-reactivation until an admin reactivates. No code changed; this is a product rule.
- [x] **Public reads hide non-discoverable records:** resolved 2026-11-12 (security review of the unauthenticated surface). The public by-id reads now follow the same rule as explore: `GET /chairs/{chair}`, `GET /chairs` and `GET /branches/{branch}/chairs` need a discoverable branch (enabled, active brand, not banned) and never show a seated barber who is not enabled or is banned; `GET /jobs/{job}` answers 404 unless the posting is open; `GET /barbers/{barber}/services` and `/slots` answer 404 for a barber who is not discoverable; `GET /branches/{branch}/reviews` answers 404 for a branch that is not discoverable; `GET /barbers/{barber}/reviews` answers 404 for a barber who is not discoverable, except to that barber themself (the stylist app's own reviews screen reads it); the barber detail's `workplaces` lists active brands only. No response shape changed and no mobile call needs an update: the only mobile caller of `GET /jobs/{job}` is the open-jobs list.
- [ ] **Contact and location fields in public barber payloads (open, found 2026-11-12):** the shared `BarberResource` returns `email`, `phone`, `latitude`/`longitude` (a freelancer's base location), `submission_count` and `email_verified_at` to guests on explore, the floor plan and chair reads, and `ApiResponseContractTest` pins `email`. Decide whether a public barber payload should carry them. Removing a field changes a contract the mobile apps parse, so it needs a coordinated app update. No code changed.
- [x] **Platform admin on affiliations and the job board:** resolved 2026-11-13, full permissions. The platform admin may list, invite, accept, reject and terminate affiliations and list, create, edit and delete job postings and manage applications on any branch. `ScopedBranchResolver::resolveForStaffing` (with `DashboardActor::canManageStaffing`: admin, manager, owner; never a barber) replaces the old `resolveForTeam` that refused the admin. Unchanged for the admin: the `job_board` plan feature, the `multi_branch` downgrade rule, the own-invite rule, the application and affiliation state machines, validation and tenant scope. The audit log names the admin as actor (`actor_type` admin, the admin's id). **Exception (Batch 1, 2026-11-13):** a Pending brand's postings cannot be created or edited by anyone, the admin included (approve the brand first); deleting and deciding on applications stay open, and the admin's audit trail now names the admin on application decisions too. **Follow-up, open:** the dashboard proxy allow-list (`proxy-allow-list.constant.ts`) still lets only managers and owners write, so the admin has no UI for this yet; changing it triggers the Playwright gate.
- [x] **Pending brand answering a barber's join request:** resolved 2026-11-13, accepting a join request counts as adding a barber (D11). `BrandStaffingGuard` refuses (403 `brand_not_approved`, the existing `BrandNotApprovedException`) a barber's join request to a branch or brand of a Pending brand, a branch's or brand's invitation, and the acceptance of any pending affiliation of a Pending brand, whoever acts, the platform admin included (approve the brand first). It runs inside the resolvers and the shared `BranchAffiliationResponder`, with the brand row locked in the same transaction, so the barber app, the branch account API and the dashboard share one rule. Rejecting and terminating stay allowed. Non-goal: rejected and suspended brands keep today's behaviour. The mobile `AuthInterceptor` no longer signs the user out on this 403.
- [x] **Brand-level affiliations closed, public job board follows the brand status, Pending postings (Batch 1):** resolved 2026-11-13. (1) A barber can no longer request a brand-level affiliation (`POST /barbers/{barber}/affiliate` answers 422 on `affiliable_type` unless it is `branch`; the resolver refuses it too): no screen, route or app can answer such a request, so it could never become Active. Existing rows are left as they are: a legacy pending brand-level row answers 400 on accept, can still be rejected by the barber when a brand sent it (a barber-initiated one has no exit and stays pending), and a legacy Active row keeps working in bookings, explore and earnings and can be ended. (2) Only an Active brand exposes postings or takes applications: `GET /jobs`, `GET /jobs/{job}` (404) and `POST /jobs/{job}/apply` (422, same answer as a closed posting) hide Pending, Suspended and Rejected brands and postings whose branch is gone; the barber's own application list is unchanged; the `job_board` plan flag is not added to the public reads. (3) A Pending brand cannot create or edit postings (403 `brand_not_approved`, every actor including the admin); delete and application decisions stay open. (4) The downgrade rule (`multi_branch` off: only the original branch is manageable) now sits in the invite resolver, so the branch API, dashboard and service layer share it, and is also applied when a branch or the dashboard accepts a request. Barber-initiated paths (a barber's join request and a barber's accept) do not get it yet, because 403 `feature_not_enabled` still signs the barber app out until the Batch 2 mobile fix. Suspended and Rejected brands keep today's behaviour. (5) Affiliation answers read the row under a lock (barber, affiliation, brand, in that order) and re-check the status, so two answers cannot both succeed; the barber row is locked on invite and request to serialise the duplicate check. (6) One application per barber per posting is a database unique index (`job_applications_posting_barber_unique`); a barber who was rejected cannot re-apply to the same posting. The migration scans first and stops with the affected pairs when duplicates exist, deleting nothing: resolve them with `SELECT job_posting_id, barber_id, COUNT(*) FROM job_applications GROUP BY job_posting_id, barber_id HAVING COUNT(*) > 1`, keep one row per pair, then migrate. (7) Application decisions and mark-seen write the status-change log (`subject_type` `job_application`, the admin named when the platform admin acts), and the branch API application list caps `per_page` at 100 (default 15).
- [x] **Backend tests run on MySQL only:** resolved 2026-11-13. SQLite is not a supported test engine (no fallback, no `:memory:`). `backend/phpunit.xml` forces `DB_CONNECTION=mysql`, `DB_DATABASE=dorak_test` and an empty `DB_URL`; host and credentials come from the gitignored `.env.testing` or the CI environment. `Tests\Support\TestDatabaseGuard`, called from `Tests\TestCase::setUpTraits` before `migrate:fresh`, throws unless `APP_ENV=testing`, the driver is `mysql` and the database is `dorak_test` or `dorak_test_<n>` (parallel workers), so the development database can never be migrated or wiped by a test run. The unused `sqlite` connection was removed from `modules/Core/Config/database.php` and the SQLite touch from `composer.json`; runtime stays MySQL. Real concurrency across two connections is still unverified (tests share one transaction).
