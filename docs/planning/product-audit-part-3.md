# Audit Findings

Part 3 of 3 · [Overview](product-audit.md) · [Matrix](product-audit-part-2.md)

| ID | Sev. | Finding |
|---|---|---|
| G1 | Major | **Resolved.** Stylists upload and tag (before/after/reference) history media on visits assigned to them via `POST /barber/history/{history}/media` (403 for anyone else's visit); stylist_app offers it from completed appointment cards and the client history screen. |
| G2 | Major | **Resolved.** Brands have a `status` (`pending` → `active`). A brand created through the API or dashboard starts `pending`; a platform admin approves it (`POST /admin/brands/{brand}/approve`, `PATCH /dashboard/admin/brands/{brand}/approve`, the dashboard Brands page, or the Filament Approve action). A pending brand is hidden from the public list/detail, and its branches cannot sign in, use the branch API or appear in discovery. Brands that existed before the gate were backfilled `active`. |
| G3 | Major | **Resolved.** business_app and stylist_app now list reviews and let a manager or stylist dispute a published one (reason 10–1000 characters); admins resolve in the dashboard. |
| G4 | Major | **Resolved.** `GET /dashboard/earnings` (owner: all own brands; manager: own branch; stylist: own completed bookings; admins use analytics) returns per-currency gross, platform commission and net (stylist: gross and net pay when an active affiliation has a commission percent). Owner-only `GET /dashboard/subscription` (plan, price, interval, features, grace date) and read-only `GET /dashboard/payouts` (own brands, drafts hidden). Dashboard pages: earnings (owner, manager, stylist), plan and payouts (owner). Mobile screens shipped with G10/G11 (stylist and business earnings). |
| G5 | Major | **Resolved.** `SmsSender` is a strategy resolved by `SmsSenderFactory` from `SMS_DRIVER` (`log` or `generic_http`). `generic_http` POSTs (JSON or form) to `SMS_HTTP_URL` with configurable headers and a payload template (`{{phone}}`, `{{message}}`), so any WhatsApp bridge or local gateway can be used without vendor lock-in. A gateway failure purges the cached code and `POST /client/phone/otp` returns 503 `SERVICE_UNAVAILABLE`. Production must set `SMS_DRIVER=generic_http`. Mobile apps unchanged. |
| G6 | Medium | **Resolved.** A brand owner (or platform admin) sets a brand-specific price and/or duration for a barber's service: `PUT /dashboard/barbers/{barber}/services/{service}/override` with `brand_id`, `price_amount_minor`, `duration_minutes` (null keeps the barber's default; at least one required), `DELETE` the same path with `?brand_id=` to restore the default, `GET /dashboard/barbers/{barber}/services?brand_id=` to list. Stored in `barber_service_overrides` (unique per service and brand), so the barber's own record and other brands are untouched. Authorized by `BarberServiceOverridePolicy`: 403 for branch managers, barbers, foreign owners, and barbers who do not work for the brand. Booking length, slots, booking payloads, commission accrual and earnings/revenue totals use the override; clients see it by passing `branch_id` to `GET /barbers/{barber}/services`. Dashboard: `/owner|admin/stylists/{id}/pricing`. Mobile apps unchanged (additive fields only). |
| G7 | Medium | **Resolved.** `EnsureBranchAccountAccess` returns 403 `ACCOUNT_NOT_ACTIVE` for any branch that is not enabled, on every `auth:branch_api` route except logout. `EnsureBarberAccountAccess` (active scope) also blocks a branch-managed barber while the managing branch is disabled. |
| G8 | Medium | **Resolved.** `POST /barber|branch/forgot-password`, `/reset-password` (6-digit emailed code, 422 for wrong/expired/unknown, tokens revoked on reset), `/logout` (current token) and `/refresh-token` (rotates the token, 403 when deactivated). business_app and stylist_app have a forgot-password flow; logout revokes the server token; the session renews its token on start. |
| G9 | Medium | **Resolved.** `POST /client/social/{provider}` only links or creates a client by email when the provider vouches for it (`email_verified` or Google `verified_email`; a missing flag counts as unverified); otherwise 403 `SOCIAL_EMAIL_NOT_VERIFIED`. Already-linked provider accounts still sign in. client_app has Google sign-in on the login screen (`SocialLoginBloc`, `SocialCredentialProvider` seam); the Google access token is exchanged through `AuthBloc` `SocialLoginSubmitted`. Apple and Facebook are intentionally unsupported (regional availability); other providers get a 404. |
| G10 | Medium | **Resolved (2026-11-03).** business_app has a bottom-nav shell with staff list (activate/deactivate), services CRUD, working hours and a notification inbox, backed by mobile-scoped `/branch/*` routes. See [mobile audit G10/G11](../mobile-audit-g10-g11/index.md). |
| G11 | Medium | **Resolved (2026-11-03).** stylist_app has past appointments, earnings, a services and pricing editor and a notification inbox behind a bottom-nav shell. See [mobile audit G10/G11](../mobile-audit-g10-g11/index.md). |
| G12 | Low | **Resolved.** Removed the unused `core` client code: `ExploreRepository.getBranches`/`getBranchesPayload`/`getBarbers` (Discovery uses `explore/search`), `HistoryRepository.updateEntry`, `ServiceCatalogRepository.getCategories`, their endpoint constants, fakes and tests. Barber reviews stay: `stylist_app` calls `getBarberReviews` since G3. Saved addresses stay device-local (no backend API; client_app uses them for profile and at-home booking). Backend routes (`PATCH /client/history/{history}`, `GET /explore/branches`, `GET /explore/barbers`, `GET /service-catalog/categories`) are unchanged. |
| G13 | Low | **Resolved.** Each portal nav entry has its own icon (`PortalNavigationIcon` covers 19 icons). `localizedName(name, locale)` replaces direct `.name.en` reads in entity lists, form options, the walk-in form, branch picker and overview, falling back to the other language when empty. Detail pages flatten nested objects (localized names, chair, barber, client) instead of dropping them. |
| G14 | Low | `business_app` and `stylist_app` AGENTS.md were stale (fixed with this audit). |
| G15 | Low | **Resolved.** `PATCH /chairs/{chair}` now accepts only `branch_api` and `admin_api` (clients get 401; the dead client branch is gone from `ChairPolicy`). Removed superseded duplicates: `POST /admin/brands/{brand}/approve`, `GET /admin/reviews`, `PATCH /admin/reviews/{review}/resolve`, and the admin-only catalog writes under `/service-catalog/items` (use `/dashboard/admin/*`); public `GET /service-catalog/*` and `GET /exchange-rates` stay for mobile. Tokens carry explicit `TokenAbility` values (`dashboard`, `branch-app`, `barber-app`, `client-active`, `email-verification`); `EnforceTokenScope` returns 403 `TOKEN_ABILITY_MISSING` when a scoped token is used outside its surface (dashboard tokens only reach `/dashboard/*`, `/notifications` and `/broadcasting/auth`). Legacy wildcard tokens keep working. No dashboard or mobile change. |
| G16 | Nit | **Resolved.** Removed 17 unused keys from `app_en.arb`/`app_ar.arb` (`avatarUpdateAction`, `bookingSelectChair`, `bookingsActionLabel`, `branchMaintenanceLabel`, `branchServicesTitle`, `chairStatusUnknown`, `historyRebookMessage`, `historyRebookTitle`, `homeTitle`, `phoneVerifyVerified`, `profileSettingsError`, `profileSettingsSaveAction`, `profileSubtitle`, `profileTitle`, `reviewCommentHint`, `reviewCommentsSection`, `reviewStarLabel`) and regenerated. `errorTitleOffline` is kept: the offline/network-error design-system states document it. Dashboard messages unchanged. |
| G17 | Medium | **Resolved.** Form Requests now bound every free-form input via `ValidationLimitConstants`: job-posting titles 150, descriptions 2000, short text and logins/passwords 255 (passwords get a maximum only, so legacy short passwords still sign in), tokens 2048, ids 36, id/tag/service lists at most 50, chair layout position/size 0–10000 (size at least 1) and rotation ±360, explore radius 0–20000 km, price filters capped, locale maps restricted to `en`/`ar`, chair `layout_settings` and catalog `price_range` restricted to known keys. Existing explicit limits (for example names at 255) were left as they were. Covered by `FormRequestBoundsTest`. |

G5, G7, G8 and G9 are launch-readiness or security work and need no product call. The rest need the decisions listed in [open decisions](../decisions-required.md).
