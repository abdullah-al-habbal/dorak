# T11. Privacy and security checks

Status: done · Phase 6 · Depends on: none · Output: a fix or a written finding for each item

- [x] T11.1 Confirm `ClientAccountDeletion` also purges face photos and face-profile data; add a test if it does not.
- [x] T11.2 Review the payment-gateway admin CRUD for credential storage; keep secrets out of ordinary admin forms.
- [x] T11.3 Check OTP, password-reset and registration endpoints for user enumeration.
- [x] T11.4 Add a production env checklist to the deployment docs (`APP_DEBUG=false`, no `log` SMS or mail driver, secure cookies).
- [x] T11.5 Check uploads for type, size and storage path rules on the face, portfolio and onboarding-hero endpoints.

Acceptance: each item is fixed with a test, or recorded as a finding with a decision.

## Findings and fixes

- **T11.1 (fixed).** Face photos were already purged after the retention window by the scheduled `face-profile:purge`, but the analysis results (face shape, features, recommended items) stayed on the soft-deleted client forever. The command now deletes them with the photos. Test: `FaceProfileLifecycleTest` ("purges the analysis results...").
- **T11.2 (no change).** `gateway_settings` is `encrypted:array`, hidden on the model, write-only in the admin API (the resource lists key names only), and an update without settings keeps the stored ones. Already covered in `PaymentGatewayTest`. Residual risk: the data is only as safe as `APP_KEY` (see the checklist).
- **T11.3 (fixed).** Staff (barber, branch) login, forgot and reset were already uniform. The client forgot-password and reset-password requests used `exists:clients,email`, so an unknown email got a different 422. Both rules are gone and an unknown email now fails like a wrong code. Test: `tests/Feature/Auth/EnumerationResistanceTest.php` (all three guards: forgot, login, reset, verify code). Not changed: registration still says an email is taken (standard, throttled to 5 per minute). Known residual: the response time of forgot-password differs slightly because mail is only sent for real accounts.
- **T11.4 (done).** Production checklist added to `docs/deployment/deployment-guide-part-3.md`. `LogSmsSender` already masks the phone and never logs the code in production, so nothing leaks, but it also sends nothing; there is no boot-time guard that refuses `SMS_DRIVER=log` there. Recorded as a decision for the owner (checklist only for now).
- **T11.5 (fixed in part).** Types and sizes were already limited (face: jpeg and png, portfolio: plus webp, hero: raster only, SVG refused, dimension cap). Face and portfolio had no pixel cap; both now refuse a side over 12000 px (`UploadConstants`). Names are generated by `store()`; face photos live on the private `local` disk under the client id, portfolio and hero on `public` by design. Test: `tests/Feature/Auth/UploadRulesTest.php`.
