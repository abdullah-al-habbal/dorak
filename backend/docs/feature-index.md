# Feature Index — Dorak Backend

> **Append entry after adding each feature.** This is the chronological map of every feature built.

### Domain-Event Notifications (Task 31)
- Queued jobs (all `afterCommit`, ID-only scalar payloads, stable `dispatchKey`, en+ar copy): `AffiliationInvitedNotification` (`invite`), `AffiliationRespondedNotification` (`invite`), `JobApplicationReceivedNotification` (`application`), `JobApplicationStatusChangedNotification` (`application`), `ReviewRequestNotification` (`review_request`).
- Triggers: `POST /barbers/{barber}/affiliate` (branch targets only), barber `POST /affiliations/{id}/accept|reject` and branch `POST /branch/affiliations/{id}/accept|reject`, `POST /jobs/{job}/apply`, `PATCH /branch/job-postings/{posting}/applications/{application}/status`, and booking completion through `BookingTransitionNotifier::statusChanged` (barber, branch and dashboard routes).
- FCM/inbox `data`: `type` (enum value), `event` (`affiliation_invited|affiliation_responded|application_received|application_status_changed|review_request`) plus IDs (`affiliation_id`, `application_id`, `job_posting_id`, `booking_id`, `status`).
- Not notified: brand-targeted affiliation requests (no notifiable actor), review requests for bookings with neither a branch nor a barber to review (Task 39). Tests: `tests/Feature/Notification/DomainEventNotificationTest.php`.

### Notification Inbox & Delivery Records (Task 30)
- Tables `notifications` (uuid, `notifiable` morph using `client`/`barber`/`branch` aliases, `type` `booking_update|invite|application|review_request`, `title`, `body`, `data`, unique `dedupe_key`, `read_at`) and `notification_deliveries` (`notification_id`, nullable `device_token_id` with `nullOnDelete`, `status` `sent|failed`, `provider_message_id`, `error`, `attempted_at`).
- `NotificationWriter` + `FcmNotificationSender::sendTo(..., NotificationTypeEnum $type, ..., ?string $dispatchKey)` — writes one inbox row per recipient (idempotent per dispatch key, so queue retries never duplicate rows or re-push delivered devices), then one delivery row per device attempt; still writes the inbox row when FCM is unconfigured or the recipient has no device.
- `GET /api/v1/notifications` — `auth:client,barber,branch_api`; unread first, newest first; `per_page` 1–100 (default 20); `meta.pagination` + `meta.unread_count`.
- `PATCH /api/v1/notifications/{notification}/read` — idempotent; another actor's ID returns 404 `RESOURCE_NOT_FOUND`.
- `POST /api/v1/notifications/read-all` — `data {updated, unread_count: 0}`.
- `NotificationDeliveryModel` is `MassPrunable` after 90 days; `model:prune` scheduled daily at 03:00 by `ApplicationServiceProvider`.

### Manager & Stylist Mobile Operations
- `PATCH /api/v1/branch/bookings/{booking}/status` — branch-authenticated booking transition to `in_progress`, `completed`, `no_show`, or `cancelled`, scoped to the manager's branch.
- `PATCH /api/v1/branch/chairs/{chair}/status`, `PUT /api/v1/dashboard/chairs/{chair}`, `PATCH /api/v1/chairs/{chair}` — moving a chair to `maintenance` returns 409 `CHAIR_HAS_ACTIVE_BOOKINGS` (`errors.booking_ids`) while future reservation-blocking bookings exist; `force=true` cancels them (`cancellation_reason = chair_maintenance`), notifies each client and lists `meta.cancelled_booking_ids`. Shared `ChairStatusService`.
- `GET /api/v1/branch/chairs` — branch-authenticated chair list, scoped to the manager's branch.
- `GET /api/v1/branch/dashboard` — daily/monthly completed-service revenue, booking/chair metrics, and the authenticated branch switcher payload.
- `GET /api/v1/barber/appointments/today` — barber-authenticated, barber-scoped appointments for today.
- `PATCH /api/v1/barber/workstation-status` — barber-authenticated online/offline workstation presence; persisted as `barbers.is_workstation_online`.
- `POST /api/v1/barber/register` — public, `throttle:5,1`; barber self sign-up (`name`, `email` unique in barbers, `password` + confirmation, optional `is_freelancer` default true, optional `phone`). Creates a `pending` barber with `has_login`, queues the email code, returns 201 `{token, barber}` (`BarberResource`, now incl. `email_verified_at`). Pending barbers cannot log in (403 `ACCOUNT_NOT_ACTIVE`) until an admin activates them (Task 37).
- `POST /api/v1/barber/email/verify/send` (`throttle:3,1`), `POST /api/v1/barber/email/verify` (`code`, `throttle:5,1`) — barber email verification; hashed 6-digit code, 10-minute TTL, 5-attempt lockout; wrong code 422 `VALIDATION_FAILED` + `errors.code`; success returns the barber.
- `EnsureBarberAccountAccess` (Task 37) gates every barber-token route on current status: `onboarding` (pending/enabled: profile read, email verification), `approved` (not pending: self activate/deactivate), default `active` (enabled: all other barber routes, including affiliations and job applications). Otherwise 403 `ACCOUNT_NOT_ACTIVE`.

### Core
- `HealthCheckAction` [GET /api/v1/health]
- `ApiResponseBodyValueObject` — standard response shape `{success, statusCode, code, message, timestamp, data, meta?, errors?}`
- `BaseApiAction` + `ApiResponseTrait` — paginated/ok/created/error/validation helpers
- `BaseModuleServiceProvider` — auto-mounts `Routes/Api/V1/*.php` at `/api/v1` with `['api']` middleware
- Auth guards: `client` (sanctum), `barber` (sanctum), `barber_dashboard` (session), `branch` (session), `branch_api` (sanctum), `admin` (session), `admin_api` (sanctum)
- Dashboard brand owner (Task 38, ADR 0001): `POST /api/v1/dashboard/login` with `actor_type = owner` authenticates a client that owns ≥1 brand (enabled, verified, not banned); the client Sanctum token carries the `dashboard` ability and the claim `brand_id` + `brand_ids`. Owners operate on every branch of their brands (branches CRUD, bookings, chairs, services, stylists, overview) via `DashboardActor::scopedBranchIds()/canAccessBranch()/canManageBrand()`; other brands → 404 (reads) / 403 (writes). `GET dashboard/me` exposes `brand_id`/`brand_ids`.
- `FcmNotificationSender` — sends per-device notifications through FCM HTTP v1 using a cached OAuth2 service-account token; prunes unregistered device tokens and retries transient failures; persists inbox and delivery records (Task 30)

## Barber history media upload (Gap G1)
`POST /api/v1/barber/history/{history}/media` (`auth:barber`) — the barber assigned to a visit
(`ClientServiceHistoryPolicy::attachMedia`) uploads a before/after/reference photo; any other barber gets 403.
Shares the handler and validation (jpeg/png, ≤5 MB) with the client upload.

## Staff password reset, logout and refresh (Gap G8)
Barber and branch accounts: `POST /api/v1/{barber|branch}/forgot-password` (throttled, never reveals whether an email exists),
`/reset-password` (emailed 6-digit code via `Core\Services\StaffPasswordResetCodes`, scoped per account type, burns after
use or too many attempts; revokes all tokens), `/logout` (current token) and `/refresh-token` (rotates the token; 403 when
the account is deactivated or banned). Managed barbers without a login cannot reset.

## Branch account gating (Gap G7)

- `Modules\Branch\Http\Middleware\EnsureBranchAccountAccess` returns 403 `ACCOUNT_NOT_ACTIVE` when the authenticated branch is not `Enabled`. It is applied to every `auth:branch_api` route (branch, settings, reviews, activation, chairs, notifications, device token) except `POST /branch/logout`, and passes other account types through.
- `EnsureBarberAccountAccess` (default `active` scope) also rejects a barber whose `managed_by_branch_id` branch is `Disabled`.
- Tests: `tests/Feature/Auth/BranchGatingTest.php`.

## Social login email verification (Gap G9)

- `SocialLoginHandler` requires the provider's verified-email flag (`email_verified` / `verified_email`, bool or string) before linking an existing client by email or creating a new one. Failure returns 403 `SOCIAL_EMAIL_NOT_VERIFIED` (`core::messages.social_email_not_verified`, EN+AR). Providers already linked by id are unaffected.
- Tests: `tests/Feature/Client/Http/Actions/SocialLoginActionTest.php`.

## Brand approval (Gap G2)

- `brands.status` (`Modules\Brand\Enums\BrandStatusEnum`: `pending`, `active`; migration backfills existing rows to `active`). Brands created via `POST /brands` or `POST /dashboard/brands` start `pending`; factories and the seeder create `active` brands.
- Admin catalog categories (Module 12): `GET|POST /dashboard/admin/catalog-categories`, `PUT|DELETE /dashboard/admin/catalog-categories/{category}`, `PATCH .../{category}/active` (`ServiceCatalogCategoryPolicy`, admin only; `AdminCatalogCategoryResource` with item, subcategory and service counts). Delete is refused with 409 `CONFLICT` unless `CatalogCategoryUsage::isEmpty()`. Shared `CatalogCategoryNameRules` and `CatalogCategorySlugGenerator` (also used by `POST /dashboard/service-categories`). Catalog item `category_id` rejects deleted categories; `ServiceRequest` keeps a service's current inactive category on update. Tests: `DashboardAdminCatalogCategoriesTest`.
- `PATCH /dashboard/admin/brands/{brand}/approve` (admin actor) sets `active` (idempotent; the old `POST /admin/brands/{brand}/approve` route is gone). `BrandPolicy::approve` (an `AdminModel` only) guards it.
- Gate: public `GET /brands` and `/brands/{id}` list active brands only; `BranchModel::isOperational()` (enabled branch + active brand) backs branch login, refresh, `EnsureBranchAccountAccess` and `scopeDiscoverable`.
- Dashboard list `GET /dashboard/brands?status=&search=&per_page=&page=` (`ListDashboardBrandsRequest`; `BrandPolicy::viewAny`: admin or brand owner, owners stay scoped; `per_page` is clamped, never rejected). API resource `status` field; the dashboard `/dashboard/admin/brands` page opens on the pending queue with a detail dialog and Approve; mobile `BrandDto.status`.
- Tests: `tests/Feature/Brand/BrandApprovalTest.php`, `tests/Feature/Dashboard/DashboardAdminBrandsTest.php`.

## Role-based earnings, plan and payout visibility (Gap G4)

Read-only dashboard endpoints (outside the admin group), scoped by `DashboardActor`:

- `GET /dashboard/earnings?from=&to=` (owner, branch manager, stylist; admin 403): completed bookings grouped per currency. Owner = all owned brands, manager = own branch → `gross_minor`, `commission_minor` (platform commission from `commission_entries`), `net_minor`, `completed_bookings_count`. Stylist = own `barber_id` bookings → `gross_minor` and `net_minor`, which is gross less the affiliation `commission_percent` and is `null` unless every booking in that currency falls under an active branch/brand affiliation with a percent.
- `GET /dashboard/subscription` (owner only): latest subscription of each owned brand with plan price, interval, feature keys, effective Pennant flags and `grace_ends_at`.
- `GET /dashboard/payouts` (owner only): own brands' non-draft payouts, paginated, `?status=`; no admin notes.

Authorization via `DashboardEarningsAuthorizationMiddleware` / `DashboardOwnerAuthorizationMiddleware`; brand and branch scope comes from the actor, never from the request. Dashboard pages: `/owner|manager|barber/earnings`, `/owner/subscription`, `/owner/payouts`. Mobile screens are deferred to G10/G11.

## Owner override of barber price and duration (Gap G6)

- `barber_service_overrides` (`offered_service_id`, `brand_id`, nullable `price_amount_minor`, nullable `duration_minutes`; unique per service and brand): a brand's own terms for a barber-owned service. A null column, or no row, falls back to the barber's default on `offered_services`. Overrides never cross brands.
- `PUT /dashboard/barbers/{barber}/services/{service}/override` (`brand_id`, `price_amount_minor`, `duration_minutes`; at least one of price or duration), `DELETE` the same path with `?brand_id=`, and `GET /dashboard/barbers/{barber}/services?brand_id=` (each service with `is_overridden` and `default_*` fields). Platform admins and brand owners only (`DashboardBrandAuthorizationMiddleware`); `BarberServiceOverridePolicy` (via `Gate::forUser($actor)`, `DashboardActor` implements `Authorizable`) additionally requires the owner to own `brand_id` and the barber to work for it (`BarberBranchMembership::belongsToBrand`: managed by one of its branches or an Active affiliation). Foreign owners, branch managers and barbers get 403; a service the barber does not own is 404.
- `EffectiveServiceTerms` resolves override-then-default for booking duration (`CreateBookingEloquentResolver`, `ListSlotsEloquentResolver`), `ServiceResource` (booking payloads, branch detail, floor plan, and `GET /barbers/{barber}/services?branch_id=`, which adds `is_overridden`, `default_price_amount_minor`, `default_duration_minutes`), `CommissionRecorder`, and the owner/stylist earnings, overview and branch dashboard revenue (`BookingServicePricing`). Without a branch context the public barber list still shows the barber's own values; explore price filters and sorting keep using the default.
- Dashboard: `/owner|admin/stylists/{id}/pricing`.

- Form Request validation bounds (Gap G17): `Modules\Core\Constants\ValidationLimitConstants` holds the shared limits and ready-made `RULE_*` strings (name 100, title 150, description 2000, short text/password 255, id 36, token 2048, lists 50, chair layout, radius, price). Password fields get a maximum only. Locale maps use `array:en,ar`. Regression tests: `tests/Feature/Core/FormRequestBoundsTest.php`.

Error keys are unchanged. English only, like the messages themselves (Arabic validation messages are not translated yet). Tests: `tests/Feature/Core/ValidationAttributeNamesTest.php`.

Routes: `GET|POST /branch/services`, `GET|PUT|DELETE /branch/services/{service}` (brand-scoped; creating for a foreign brand is 403, a foreign service 404), `GET /branch/barbers` (staff of the branch, via chairs), `GET /branch/earnings` (scope `branch`), `GET /barber/earnings` (scope `barber`), and `GET /barber/appointments` (own history, newest first; `status`, `from`, `to`, `per_page` ≤ 50; `BookingPolicy::viewOwnHistory`). Staff activate/deactivate stays `POST /branch/barbers/{barber}/(de)activate`; working hours are read from `GET /branch/profile` (`opening_hours`) and written by `PUT /branch/opening-hours`. Tests: `tests/Feature/Mobile/MobileScopedRoutesTest.php`.

- Dashboard list contracts (web dashboard modules 1-2): `GET /dashboard/bookings` accepts `hide_cancelled=1`; `GET /dashboard/stylists` accepts `chair_id` and `status` and each row carries `chair {id,label,branch_id}`; `GET /dashboard/services` rows carry `category {id,name{en,ar}}` (from the catalog item); `GET /dashboard/currencies` (Operations group) lists currencies. All additive, so existing mobile consumers are unaffected. Tests: `BookingApiTest`, `StylistApiTest`, `ServiceApiTest`.

- Dashboard service categories: `offered_services.category_id` (nullable FK to `service_catalog_categories`, `nullOnDelete`) lets a service carry its own category; `ServiceRequest` accepts `category_id` (active, non-deleted category). The dashboard service payload's `category {id,name{en,ar}}` resolves the service's own category first, then its catalog item's. `GET /dashboard/service-categories` lists active categories and `POST /dashboard/service-categories` creates one (`name{en,ar}`, unique per language, slug generated server-side); both sit in the Operations group, so admins, managers and owners can use them and barbers get 403. Categories are platform-wide, so a created category is visible to every brand. Tests: `ServiceApiTest`.
- Dashboard earnings series: `GET /dashboard/earnings` still returns `scope` and `totals`, and now adds `series` (revenue and completed bookings per UTC calendar day and currency, for the same bookings the totals cover; `EarningsSeriesEloquentResolver`), `previous_period` and `previous_totals` (the equal-length range ending the second before `from`; both null unless `from` and `to` are sent). Additive, so existing mobile clients are unaffected. Tests: `tests/Feature/Dashboard/DashboardEarningsVisibilityTest.php`. Also `DASHBOARD_LOGIN_ATTEMPTS_PER_MINUTE` (default 5) sets the dashboard login throttle; `/dashboard/owner/brand` has its own named limiter and counter (`DASHBOARD_OWNER_BRAND_ATTEMPTS_PER_MINUTE`, defaults to the login value).

A PUT replaces only the listed days. `BranchHours::covers()` (slots, booking creation, dashboard reschedule) requires the booking to fit inside one shift, so the gap between shifts is not bookable. Dated overrides stay single-interval. New dashboard routes `GET|PUT /dashboard/branches/{branch}/opening-hours` (Operations group; PUT body `{hours: [...]}`, same branch-scope checks as `PUT /branches/{branch}`) so the editor no longer resends the whole branch. Tests: `tests/Feature/Dashboard/BranchOpeningHoursApiTest.php`.

Tests: `tests/Feature/Dashboard/ChairApiTest.php`.

Create (`POST`) and delete (`DELETE`) stay limited to platform admins and the brand's owner (`DashboardActor::canManageBrand`). Additive, so mobile consumers are unaffected. Tests: `tests/Feature/Dashboard/BranchApiTest.php`.

It counts published and resolved reviews only (the same set as `SubjectRatingRefresher`, so it matches the branch `rating_average`/`rating_count`); `average` is null when nothing is counted. Computed by `Modules\Review\Services\BranchReviewSummary`. Additive, so mobile consumers are unaffected. Tests: `DashboardBranchOperationsTest`.

A `date_to` that carries a time keeps its exact instant; `date_from` is unchanged. Tests: `BookingApiTest`.
- Dashboard barber schedule (web dashboard module 8): `GET /dashboard/schedule/appointments` (`booking_status`, `date_from`, `date_to` as `YYYY-MM-DD` and inclusive, `per_page` max 50; earliest first; `StaffBookingResource` payload with `meta.pagination`) and `GET /dashboard/schedule/hours` (`id, day_of_week, start_time, end_time, is_active`, one row per weekday). Barbers only via `DashboardBarberAuthorizationMiddleware` (403 for other actors; the Operations group still rejects barbers) and `BarberSchedulePolicy::viewOwn`; the barber id is the session actor, never client input. New routes only, so mobile consumers are unaffected. `E2eDashboardSeeder` seeds the barber's password and hours. Tests: `tests/Feature/Dashboard/BarberScheduleApiTest.php`.
- Dashboard admin billing (web dashboard module 9): the admin payout (`/admin/payouts`, `generate`, `approve|mark-paid|cancel`) and plan/subscription (`/admin/subscription-plans`, `/admin/plan-feature-keys`, `/admin/subscriptions`, `/admin/subscriptions/{id}/status`) routes drive the dashboard admin screens. Changes: `TransitionPayoutHandler` and `UpdateSubscriptionStatusHandler` re-read the row with `lockForUpdate` inside the transaction so concurrent admins cannot both pass the state machine (a stale copy yields 409); `GET /admin/subscriptions` accepts a validated `status` (`ListBrandSubscriptionsRequest`); `GET /admin/subscription-plans` accepts a validated `is_active` (`ListSubscriptionPlansRequest`). Admin-only for every other guard (403). Tests: `AdminBillingManagementTest` plus the existing `PayoutTest` and `SubscriptionPlanTest`.
- Dashboard platform analytics and settings (web dashboard module 10): `GET /dashboard/admin/analytics/overview` accepts validated `from` and `to` dates (`ShowPlatformAnalyticsRequest`, `to` on or after `from`). The range narrows the flow figures: `completed_bookings`, new `bookings_by_status` and `completed_bookings_series` (by `bookings.starts_at`), and commission and payouts (by `created_at`); subscriptions and the new `platform` totals (`brands, branches, barbers, clients`) stay live. `by_plan` rows gain `plan_name`; `period` echoes the range. All existing keys are unchanged, so mobile is unaffected. `PATCH /admin/settings` gains two cross-field rules (`UpdatePlatformSettingsRequest::withValidator`, en and ar messages): the default page size cannot exceed the maximum, and the dashboard refresh lifetime cannot be shorter than the session lifetime (effective value = submitted, else stored; 422 keyed `settings.<key>`). Owner analytics need no new route: brand-scoped figures stay on `GET /earnings` and `GET /overview`. `E2eDashboardSeeder` clears `platform_settings` on every reset. Tests: `PlatformAnalyticsTest`, `PlatformSettingsTest`.

## Dashboard password recovery and account sessions (NS-01, NS-02)
- `POST /api/v1/dashboard/password/forgot` (always the same answer; mail deferred; 5/min per IP + 5/hour per email) and `POST /api/v1/dashboard/password/reset` (5/min per IP; generic 422 `token` error for a bad, used, expired or no-longer-eligible link). Built on `auth.passwords.*` brokers; tokens are hashed, single use, 60 minutes. Code: `Modules\Dashboard\Handlers\Password`, `Services\DashboardPasswordResetLinkSender`, `DashboardCredentialRevoker`, `DashboardMobileResetCodeCleaner`, `Repositories\DashboardPasswordResetAccountResolver`, limiters in `DashboardServiceProvider::registerPasswordResetLimiters`. Config: `dashboard.dashboard.frontend_url` (`DASHBOARD_URL`), `trustedproxy.proxies` (`TRUSTED_PROXIES`).
- A reset revokes all of the account's dashboard sessions and clears its mobile reset code; a mobile reset (client, branch, barber) deletes the dashboard broker token. `PUT /dashboard/profile/password` now ends the account's other sessions: it keeps the current access token and the refresh token sent as `refresh_token` (all refresh tokens are revoked when none is sent), and deletes the broker token and mobile code.
- Tests: `tests/Feature/Dashboard/DashboardPasswordResetApiTest.php`, `DashboardPasswordResetThrottleTest.php`, `DashboardPasswordChangeSessionTest.php`.

## Owner self-registration (NS-03)
- Public `POST /api/v1/dashboard/owner/{register,code/resend,verify,brand}`: one answer for every email, verify opens the owner session, an existing client adds a brand with their password. Limits 5/min per IP and 5/hour per email (verify 10 and 10).
- `BrandApprovalGuard` (D11) keeps a pending brand to its profile and one prepared branch; the dashboard brand list and approval only see verified owners; `OwnerBrandMailer` sends the submitted, approved and rejected emails (en and ar, queued); `signups:purge-unverified` removes sign-ups unverified after 7 days.
- Tests: `tests/Feature/Dashboard/OwnerRegistrationTest.php`, `tests/Feature/Seeders/E2eDashboardSeederTest.php`.

## Currencies and exchange rates (NS-19)
- Admin-only `GET|POST /api/v1/dashboard/admin/currencies`, `PUT .../{currency}`, `PATCH .../{currency}/active` and `GET|POST /admin/exchange-rates`, `DELETE /admin/exchange-rates/{rate}`; writes go through `CurrencyPolicy`.
- `currencies.is_active` (default true): a currency is retired, never deleted; the default currency can't be retired (409). The public and operations `GET /currencies` list active currencies only; conversion still works for retired ones. Rates are a history, the newest one in effect wins.

## Languages (NS-20)
- Admin-only `GET /api/v1/dashboard/admin/languages` and `PATCH .../{language}/active`, authorized through `LanguagePolicy`. `languages.is_active` (default true) switches an existing language on or off; the default language can't be switched off (409). No create or delete: a new language needs translations in code. Nothing else reads the flag yet.

## Catalog tags (NS-21)
- Admin-only `POST /api/v1/dashboard/admin/catalog-tags`, `PUT .../{tag}` and `DELETE .../{tag}` (soft delete), authorized through `ServiceCatalogItemTagPolicy`; the slug is generated from the English name. `GET /admin/catalog-tags` now also returns `slug`, `is_active` and `items_count`. Item CRUD (`/admin/catalog-items`) was already served and is now used by the dashboard.

## Payout detail (NS-24)
- Admin `GET /api/v1/dashboard/admin/payouts/{payout}` now also returns `approved_by` and `updated_at`; new `GET .../{payout}/entries` lists, paginated, the commission entries a payout settles (its lines), authorized through `PayoutPolicy::view`. The payout status history is derived from `created_at`, `approved_at` (+ approver), `paid_at` and, for a cancelled payout, `updated_at`; there is no separate status log.

## Website content admin (NS-25)
- Admin-only, `MarketingContentPolicy` (pages, sections, testimonials) and `OnboardingConfigurationPolicy`: `GET /dashboard/admin/marketing-pages` (pages with ordered sections, plus all testimonials), `PUT .../marketing-pages/{page}` (titles, meta descriptions; the slug is fixed), `PUT .../marketing-sections/{section}` (title, subtitle, structured per-locale body capped at 20,000 bytes, media path, order, audience; page and type are fixed), `POST|PUT|DELETE .../testimonials`, `GET .../onboarding-configs`, `PUT .../onboarding-configs/{config}` (`is_active`, `sort_order`). ## Dashboard security hardening (post NS-25 review)
- **Job board is the shop team's, and the platform admin's (decision 2026-11-13):** the dashboard job-posting writes, `GET .../applications`, `POST .../applications/mark-seen` and the application status route accept the platform admin, a branch manager and a brand owner (`ScopedBranchResolver::resolveForStaffing`, each inside their own scope); the dashboard proxy allow-list still lets only managers and owners write until the dashboard batch. Reading a branch's postings stays open to the admin (NS-09).
- **Reads do not write:** `GET /dashboard/branches/{branch}/job-postings/{jobPosting}/applications` no longer marks anything as seen. The dashboard calls `POST .../applications/mark-seen` when a vacancy is opened. It is idempotent, limited to that posting, and moves `submitted` applications to `seen` only; the response is `{updated: n}`. The mobile route follows the same contract: `GET /branch/job-postings/{id}/applications` is read-only, and the business app calls `POST /branch/job-postings/{id}/applications/mark-seen` (branch-scoped to its own posting, 404 for another branch's, repeat calls return `{updated: 0}`) before it loads the list, treating a failure as non-fatal. Both routes share `ApplicationSeenMarker`. Compatibility note: business-app builds released before this change no longer move applications to `seen` when they list them; the status is informational (accept and reject still work from `submitted`), and it catches up once the manager updates the app.
- **Barber lookup:** `GET /dashboard/barber-lookup` is limited to 30 requests a minute per signed-in account (limiter `dashboard-barber-lookup`, answer 429), because an exact email or phone confirms that a stylist exists.
- **Website images:** `media_url` (sections) and `avatar_url` (testimonials) accept empty, a path on this site (`/images/hero.jpg`), or an https URL on this site's host, the public disk's host or a host listed in `marketing.trusted_media_hosts` (`modules/Marketing/Config/trusted_media_hosts.php`). `javascript:`, `data:`, protocol-relative, `http:`, userinfo, foreign hosts and `..` are refused (422). A value already stored can be saved again unchanged (`TrustedMediaUrlRule`).
- **Legacy admin branch activation follows the lifecycle rules:** `POST /admin/branches/{branch}/activate|deactivate` (guard `admin_api`, no known client) used to write only an `activation_logs` row that an observer copied onto the branch, so it could lift a suspension or skip the plan limit and the status history. Both routes now call `BranchLifecycleService` (`switchOn`/`switchOff`) first: a suspended branch answers 409, the last enabled branch of a brand cannot be switched off, and the move is written to `status_change_logs`; the response is still the activation log. The acting admin is stored in `activated_by_id`. Barber activation through `/admin/barbers/{barber}/activate|deactivate` and `/branch/barbers/{barber}/activate|deactivate` now answers `409` with code `barber_not_approved` for a pending or rejected barber (`BarberActivationService::ensureToggleable`); the `201` and the activation log response are unchanged, and repeating an on or off for an approved barber stays allowed. Open question: whether the barber's own `/barbers/{barber}/activate` may undo an admin deactivation (see `docs/backlog/index.md`).
- **Branch switch permission (D9):** `PATCH /dashboard/branches/{branch}/switch-on|switch-off` is for the owner and the admin only. Branch managers get 403 from the route middleware and the dashboard proxy now refuses them too.
- **Deactivated admins cannot renew a dashboard session:** `POST /dashboard/refresh` refuses (401) and revokes the refresh token of an admin who is deactivated or deleted (`DashboardRefreshTokenResolver::activeAdminActor`). Before this, the call still issued a token that the dashboard middleware then rejected on every request.
- **Public reads hide non-discoverable records:** `GET /chairs/{chair}`, `GET /chairs` and `GET /branches/{branch}/chairs` use `ChairModel::discoverable()` (the branch must be discoverable) and `concealUndiscoverableBarber()` (a disabled, rejected, pending or banned seated barber is returned as `null`, so `rejection_reason` never leaks). `GET /jobs/{job}` serves open postings only. `GET /barbers/{barber}/services`, `/slots` and `GET /branches/{branch}/reviews` answer 404 for a barber or branch that explore hides; `GET /barbers/{barber}/reviews` also answers 404 except to the signed-in barber reading their own. The barber detail's `workplaces` lists active brands only. Tests: `tests/Feature/Explore/PublicReadsHideNonDiscoverableTest.php`. Open question: contact and location fields in the shared `BarberResource` (see `docs/backlog/index.md`).
